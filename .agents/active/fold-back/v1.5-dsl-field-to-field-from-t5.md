# v1.5 DSL increment — field-to-field comparison (scoped NARROW, justified by t5)

**Decided:** 2026-06-29 (owner ruling). **Status:** scoped; implementation is POST-DEMO.
**Trigger:** PR #207 (graph-backend-adapter-contract t5) worked example.

## Decision
Promote **field-to-field comparison** into the KG DSL as a v1.5 increment, justified by the
t5 worked example as a **§12.4 blocker fast-path** case (a verified blocker with no clean v1
workaround), NOT on breadth. Keep the increment **narrow** — field-to-field only. Log the
genuinely-broad demand (ORDER BY, reverse/undirected traversal) as **separate** §12 budget
items for a later, breadth-driven v1.5 design review.

## Why this is the right framing (the "worked example as v1.5 score")
A meaningful worked example's job is to stress a real query against the DSL and reveal the
expressiveness ceiling. t5's view ("compliance evidence referencing a symbol that **changed
since the evidence was collected**", spec §8.3 `f.last_changed > e.collected_at`) is the first
real cross-adapter compliance question, and it immediately needs field-to-field comparison,
which v1 **§5.1 explicitly forbids**. That failure is empirical proof v1 is under-powered for
the actual workload — it converts the on-paper §12 candidate from "someday" to "required."
Retargeting the view to an easier predicate (the rejected option) would have *suppressed* this
signal; we keep it pointed at the hard predicate and extend to meet it.

## Adapter survey verdict (breadth check, 2026-06-29)
- **Field-to-field as a hard blocker: t5 ALONE.** No other shipped/spec'd view compares two
  note fields with no v1 escape.
- **Same temporal "changed-since" semantic, but NOT blocked:** citation (§13.4) and
  document-cross-ref (§13.5) satisfy it via the reactive `source_mutation` driver / over-taint
  model — they'd gain *precision*, not *capability*, from v1.5. Not justification.
- **`stale_evidence_unsupported_controls`** (compliance) is field-vs-`now` (v1-expressible) +
  has an env-predicate escape — the *precedent* for t5's approximation, not a second blocker.
- **The real accumulated breadth points elsewhere:** ORDER BY (ttrpg WISHLIST + CRG flows
  parity §11.1, 2 sites), reverse/undirected + zero-hop traversal (ttrpg + spec Q7, 2 sites),
  shortest-path/paths, avg/sum, OPTIONAL WHERE. **None is field-to-field.** These are the
  candidates for a separate breadth-driven v1.5 review — do NOT bundle them into this increment.

## Scoped increment (NARROW — post-demo)
1. **t4 CRG schema** (`internal/adapters/builtin/crg/schema.yaml`): add a queryable
   `last_changed` (timestamp) field on the `symbol` note type. The `source_mutation` driver
   already knows this value (`.stale.fired_at`). **This is t4 write scope** — separate task /
   owner sign-off; it is additive, not a defect fix.
2. **DSL grammar** (`internal/kg/dsl/...`): allow field-to-field comparison in WHERE
   (relax §5.1 for two-field operands), bumped under `dsl_version` (spec Q5 anticipates v1.5
   versioning). Smallest grammar change that unblocks the predicate.
3. **t5 view** (`internal/adapters/builtin/compliance-register/views/views.go`): compute the
   TRUE predicate `f.last_changed > e.collected_at` (or `s.stale.fired_at > e.collected_at`),
   drop the `ApproximationNotice`, and rename/keep the view to its honest meaning.
4. **Un-mask the test** (`views/views_test.go` + `testdata/cross-adapter/`): add a fixture row
   that exercises the divergence the old approximation hid (evidence collected AFTER the symbol
   changed) and assert the now-CORRECT result. The current fixture is rigged so the wrong
   predicate yields the right answer — that must no longer pass by construction.

## Spec edits to land with the increment

- §8.3 / §12: record t5 as the §12.4 blocker that triggered the increment; move ORDER BY +
  traversal to an explicit "v1.5 breadth review (separate)" subsection with their evidence.
